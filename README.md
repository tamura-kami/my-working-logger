# My Working Logger

個人用の作業時間記録アプリ。仕様は [docs/specification.md](docs/specification.md)。
React / TypeScript / Vite、Hono API、Workers Static Assets、D1 の実行基盤と3画面の枠を用意しています。カテゴリ・作業管理、通常タイマー、作業別設定のポモドーロ、最近の実績一覧を実装しています。日別タイムラインと実績編集・削除に対応しています。週・月集計は後続 issue で追加します。

## ローカル開発

Node.js 22.12 以上（推奨: Node.js 22 LTS）と npm を使用します。Cloudflare アカウントへのログインはローカル開発には不要です。

```sh
npm ci
npm run db:migrate:local
npm run dev
```

表示された URL（通常 `http://127.0.0.1:5173`）で画面を開きます。同じオリジンの `/api/health` が `{"status":"ok","database":"ok"}` を返します。未マイグレーションの場合は 503 です。

- `/`: タイマー（Safari 15 必須対応の入り口）
- `/summary`: 実績・サマリ
- `/projects`: 作業管理

Cloudflare Vite plugin が実際の Workers ランタイムとローカル D1 を起動します。Vite と Wrangler は共通の `.wrangler/state` を使用し、ローカル DB は再起動後も保持されます。`db:migrate:local` は適用済みマイグレーションを再実行しません。本番 DB には接続しません。

## 検証・ビルド

```sh
npm run check
npm run preview
```

`check` はフロント・Worker・設定/テストの型検査、Vitest、ビルドを実行します。テストは独立した一時 D1 でマイグレーション、API、参照制約、タイマーのローカル復元と実績再送を確認し、DOM 環境で画面の操作・復元も確認します。`preview` はビルドした Worker と画面をローカルで動かします。

ブラウザ JS と CSS のビルド対象は Safari 15 です。画面は直接の動的 import で分割し、サマリや管理画面の依存をタイマーに静的 import しないでください。新しい Web API は対応状況を確認してから使用し、必要なら検出・代替処理を用意します。ビルド対象の指定だけでは Web API の互換性は保証されません。iPadOS 15 の Access ログインと実際の記録操作は後続 issue で実機検証します。

## 環境設定と秘密情報

`wrangler.jsonc` に Worker、Static Assets、D1 の設定を置きます。`DB` が D1 の binding 名です。`database_id` は作成済みの本番 DB の ID を設定しています。別の Cloudflare アカウントへ配置する場合は、そのアカウントで作成した DB の ID に変更してください。DB ID は秘密情報ではありません。`--local` を指定した開発・マイグレーションは本番 DB へ接続しません。

現時点でアプリの環境変数・秘密情報は不要です。将来ローカルの秘密情報が必要になったら `.dev.vars.example` を `.dev.vars` にコピーします。本番の秘密情報は `npx wrangler secret put 名前` で登録します。`.dev.vars*`、`.env*`、ローカル DB、ビルド成果物は git の対象外です（example ファイルを除く）。`VITE_` の値はブラウザへ公開されるので秘密情報を入れないでください。

## カテゴリ・作業管理と通常タイマー（issue #3 / #4）

「作業管理」でカテゴリと作業を作成・改名できます。作業はカテゴリ1つと表示色を必須とし、アーカイブ/解除できます。標準「未分類」は固定で変更・削除不可です。カテゴリ削除時は所属作業を未分類へ移し、作業と実績を保持します。作業の削除は提供せず、アーカイブで候補から外します。

タイマーで非アーカイブ作業を選び、「開始」「一時停止」「再開」「終了して保存」を操作します。作業変更は終了後のみ可能です。開始後に作業がアーカイブされても、現在のタイマーは終了できます。終了時に確認ダイアログを表示し、実作業が1秒未満（秒表示で0秒）なら実績を破棄します。「実績・サマリ」で最近100件の保存結果を確認できます。

### 新しいマイグレーションを適用

```sh
npm run db:migrate:local
npm run dev
```

本番更新時は、配置より先に新しいテーブルを作成します。

```sh
npm run db:migrate:remote
npm run deploy
```

`0005_local_timer.sql` が旧タイマー状態・操作履歴を撤去し、実績再送用の `session_receipts` を追加します。既存の確定実績・カテゴリ・作業は保持します。**更新前に旧版で進行中のタイマーを終了・保存してください。旧サーバーの進行中タイマーは移行しません。** healthはスキーマversion 5を確認します。

### ローカルタイマー（issue #14）

開始・一時停止・再開・フェーズ切替はブラウザだけで処理し、通信を待ちません。`my-working-logger.timer.v1` にversion 1の実行状態と未保存実績をまとめて保存します。端末間・タブ間の進行中タイマー共有は行いません。

通常タイマーは計測中に閉じても時間が進み、一時停止中はそのまま復元します。計算には `Date.now()` と基準時刻の差を使い、負の経過時間を防ぎます。

ポモドーロの設定は作業別に保持し、開始時にローカル実行状態へ複製します。表示中は集中→短休憩→集中→長休憩を自動で進めます。初期化・復帰時に満了していた場合は現在フェーズを予定時刻で確定し、00:00で停止します。次フェーズは明示操作で開始します。更新間隔が5秒以上空いた場合も停止からの復帰として扱い、複数フェーズを遡及進行しません。

長休憩直前のサイクル実績と途中終了までの集中時間だけをD1に保存します。短休憩・停止・同一サイクル内の空白は休止時間に含み、長休憩は含めません。実作業1秒未満は保存しません。

保存失敗時は未保存実績を残し、再表示・オンライン復帰・再送操作で同じIDを再送します。タイマー操作は継続できます。APIは元内容を実績とは別に保持し、編集・削除後も二重登録・上書きを防ぎます。終了後は実行状態を削除し、未保存実績もなくなると保存キーを削除します。

Storage書込み失敗時は操作を確定せず通知します。破損・読込み不可・未対応バージョンは自動削除せず操作を止めます。ブラウザのサイトデータ削除はタイマーと未保存実績も失わせるため、復旧はデータを保護して行ってください。

### API

全 API は Access の保護対象です。更新は JSON を送信し、ブラウザの別オリジンからの操作を拒否します。

| メソッド / パス | 用途 |
| --- | --- |
| GET / POST `/api/categories` | 一覧 / 作成（`name`） |
| PATCH / DELETE `/api/categories/:id` | 改名 / 削除と未分類への移動 |
| GET `/api/projects` | 非アーカイブ作業。`?scope=all` で全作業 |
| POST `/api/projects` | 作成（`name`、`category_id`、`color`） |
| PATCH `/api/projects/:id` | 名前・所属・色・`archived` の部分更新 |
| POST `/api/sessions` | 確定実績保存（`id`, `project_id`, `started_at`, `ended_at`, `paused_ms`） |
| GET `/api/sessions` | 最近100件の実績 |

入力不正は400、作業なしは404、同じ実績IDで内容が異なる再送は409です。同じIDと内容の再送は保存済みとして成功します。旧 `/api/timer` は撤去しています。

### 手動確認（PC と iPadOS 15 / Safari 15）

1. 作業管理でカテゴリと作業を追加。色と所属を変更して保存する。
2. タイマーで作業を選び開始。リロードとタブを閉じて再オープンを行い、作業と時間が復元することを確認する。
3. 一時停止して時間を置き、実作業表示が止まり停止合計が増えることを確認する。一時停止中にもリロード・タブ再オープンを行う。
4. 再開後に終了確認をキャンセルすると計測が続き、確認すると実績一覧に1件だけ保存されることを確認する。
5. 2タブ・2端末から同時に開始/終了して、最大1つのタイマーと1件の実績だけになることを確認する。
6. 作業をアーカイブすると新規選択候補から消え、実績一覧には残ることを確認する。カテゴリを削除して作業が未分類へ移り、実績も残ることを確認する。
7. 通信を切って操作し、エラー表示と接続復帰後の同一操作再送を確認する。すでに保存されていた場合も二重保存されないことを確認する。

自動テストではローカル D1 で参照制約、状態遷移、時間計算、競合、再送、途中失敗時のロールバックを検証します。iPad での Access ログインは確認報告を受けていますが、通常タイマー・ポモドーロ操作の実機検証は未実施です。ポモドーロは各時間を1分に設定し、作業別設定の再読込、集中の一時停止・再開・途中終了、集中→短休憩→集中→長休憩→集中の自動移行、長休憩直前の実績保存、短休憩中の途中終了、休憩スキップ、バックグラウンド復帰時の満了停止、画面を閉じて満了後に開き直す操作を確認してください。

## Cloudflare Access と本番デプロイ（issue #2）

認証・許可判定は Cloudflare Access に任せます。アプリ内にはログイン画面、パスワード、ユーザー登録、独自の認証処理を作りません。Access はローカル開発には適用されません。ローカルの Vitest が通っても本番の Access 保護を確認したことにはならないため、以下の本番確認が必要です。

### 1. 公開経路を作らずに Worker を配置

必要なものは Cloudflare の Workers / D1 / Zero Trust を操作できるアカウントと、ログインに使うメールを受信できる端末です。独自ドメインは任意です。Zero Trust 未設定の場合はダッシュボードでチーム名などの初期設定を完了します。プラン・利用枠は契約時に確認してください。

```sh
npm ci
npx wrangler login
npx wrangler whoami
npx wrangler d1 create my-working-logger
```

出力された `database_id` を `wrangler.jsonc` に設定します。binding 名 `DB` と `migrations_dir` は維持します。次に本番 DB を初期化して配置します。

```sh
npm run db:migrate:remote
npm run deploy
```

`db:migrate:remote` は本番 DB への書き込みです。`deploy` は型検査・テスト・ビルド後に、フロントと API を単一 Worker として配置します。Cloudflare Vite plugin が生成した Wrangler 設定を利用するため、`dist/` を直接編集しません。

初回配置時は `workers_dev: false`、`preview_urls: false`、カスタムドメイン・ルート指定なしにします。現在の設定は Access 設定後に `workers_dev: true` としているため、新規アカウントへ配置する際は先に `false` に戻してください。新規 Worker の初回配置では HTTP の公開入口を作りません。これは未認証のアクセスを通す期間を避けるための準備状態であり、Access の代わりではありません。

既存 Worker に適用する場合は、先にダッシュボードの **Settings > Domains & Routes** とプレビュー設定を確認します。設定ファイルに書かれていない既存の経路が無効になると想定せず、すべての経路を保護するか無効化してください。公開経路を追加するのは、次の Access 設定が完了してからです。

### 2. 許可メールのポリシーを用意

1. Cloudflare ダッシュボードの **Zero Trust > Integrations > Identity providers** で **One-time PIN** を追加します。アプリ側にメール送信処理は不要です。
2. **Zero Trust > Access controls > Policies** で再利用できるポリシーを作成します（UI によっては Applications 内のポリシー編集から作成）。名前を `my-working-logger-owner`、Action を **Allow** とします。
3. **Include > Emails** に、アクセスを許可する自分のメールアドレスを完全一致で登録します。複数許可する場合もアドレスを個別指定します。メールドメイン全体や Everyone は選びません。
4. Allow に一致しない利用者は拒否されます。**Bypass**、**Service Auth**、Everyone やメールドメインを許可する別のポリシーは、この個人用アプリに追加しません。複数の Allow ポリシーがあると、別のポリシー経由でも許可されるためです。

### 3. Worker 全体に Access を適用

1. **Workers & Pages > my-working-logger > Access** を開き、**Protect this Worker behind Access** を選びます。
2. 対象を **All traffic**（本番とプレビューの両方）にします。**Previews only** では本番を保護できません。
3. Authentication policy に手順2の `my-working-logger-owner` を選択して **Apply Access** します。画面に完全一致メールの設定が出ない場合も、広い許可を代わりに選ばず、Zero Trust で作成したポリシーを指定します。
4. Zero Trust の該当 Access application を開き、対象がこの Worker 全体であること、Allow が手順2のポリシーだけであること、ログイン方式に One-time PIN が含まれることを確認します。セッション時間は初期運用では24時間を目安に設定します。

Worker 全体の Access は、関連する workers.dev、カスタムドメイン、ルート、プレビューの入口をまとめて対象にします。画面だけでなく `/api/*` と静的 JS/CSS も対象です。`/api/health` も例外にはしません。アプリで Access ヘッダーの有無だけを信用する認証は追加しません。

Worker 全体の設定が利用できない場合は、公開を保留し、[ホスト名単位の Access 設定](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/)を使用します。Self-hosted application の対象はホスト全体（Path 空欄）にし、すべての公開ホストへ手順2のポリシーを適用します。プレビューは無効のままにします。API だけ、ルート画面だけを保護する設定では不十分です。

### 4. 保護設定後に公開入口を有効化

独自ドメインがなくても、以下の設定で利用できます。

1. `wrangler.jsonc` の `workers_dev` を `true` に変更します。`preview_urls` は `false` のままにします。
2. `npm run deploy` を実行し、表示された `https://my-working-logger.<account-subdomain>.workers.dev` を利用します。
3. **Domains & Routes** と **Access** をもう一度開き、公開された入口が手順3の保護対象であることを確認します。

独自ドメインを使う場合は、Cloudflare 管理下のドメインであることを確認し、Access 設定後に `wrangler.jsonc` に次のような実際のホスト名を設定して再配置します。例示のホスト名は置き換えてください。

```jsonc
"workers_dev": false,
"preview_urls": false,
"routes": [
  { "pattern": "logger.example.com", "custom_domain": true }
]
```

これで独自ドメインを入口とし、workers.dev を無効のままにできます。ダッシュボードだけで公開 URL の有効・無効を切り替えず、Wrangler の設定も一致させます。プレビューが必要になったら、先に **All traffic** の保護を確認してから有効化し、新しい URL でも以下の確認を繰り返してください。プレビューは本番 D1 を共有することがあるため、書き込み検証には別 Worker / 別 D1 を用意します。

### 5. 保護漏れと認証の確認方法

配置直後と公開経路・ポリシー変更後に、次の表を確認します。無効の経路は「無効」と記録し、未確認のまま合格扱いにしません。

| 公開されうる経路 | 確認対象 | 期待結果 |
| --- | --- | --- |
| workers.dev | `/`、`/summary`、`/projects`、`/api/health`、`/api`、`/api/missing` | 有効なら Access 保護、不要なら無効 |
| カスタムドメイン・既存ルートの全ホスト | 同上（ルート指定ならその配下） | すべて Access 保護 |
| Version URL・プレビュー・preview alias | 既存 URL、新しく生成された URL、各パス | 初期運用では無効。使う場合はすべて Access 保護 |
| 配置された JS/CSS | ログイン後の HTML から確認した実際の `/assets/...` | 未認証で取得できない |

未認証の確認では、Cookie や Access トークンを付けず、リダイレクトを追わずに GET します。以下の例のホスト名を実際の公開ホストに置き換え、表の全パスで実行します。

```sh
curl --silent --show-error --dump-header - --output /dev/null 'https://my-working-logger.<account-subdomain>.workers.dev/'
curl --silent --show-error --dump-header - --output /dev/null 'https://my-working-logger.<account-subdomain>.workers.dev/api/health'
```

Access のログイン URL へのリダイレクト、または Access による拒否を確認します。2xx でアプリの HTML、JS/CSS、health の JSON が返れば保護漏れです。アプリ自身の 404/503 や無関係なリダイレクトも、保護成功の証拠にはなりません。無効の入口は Worker の画面/API が返らないことと、ダッシュボード上の無効設定の両方で確認します。

ブラウザでも次を実施します。

- **未認証**: 新しいプライベートウィンドウで画面と API の URL に直接アクセスし、Access に止められることを確認。
- **許可ユーザー**: 許可メールで One-time PIN にログインしてタイマー画面に到達。画面の遷移・再読み込み、直接開いた `/api/health` の `200` と `{"status":"ok","database":"ok"}`、`/api/missing` の JSON 404 を確認。
- **未許可ユーザー**: 別のプライベートセッションで、許可一覧にない受信可能なメールを使ってログインを試みる。PIN が届かない場合も含め、画面・API が利用できないことを確認。PIN の発行有無だけで判定しない。
- **セッション終了**: `https://<公開ホスト>/cdn-cgi/access/logout` でログアウトし、画面と API を開き直して再認証が必要なことを確認。期限切れのセッションでも再認証されることを確認。

Zero Trust の Access ログで許可・拒否の結果とポリシーを照合します。PIN、Cookie、JWT、メールアドレスを含む認証ログをリポジトリに貼り付けないでください。

### 6. iPadOS 15 / Safari 15 の確認

実機の iPadOS バージョンを記録し、Safari で次を検証します。PC のエミュレーションだけでは合格としません。

- 未認証から Access のメール入力、PIN 受信・入力、タイマー画面への復帰まで完了する。
- リロードやタブを閉じて開き直した場合に、ログイン済みならタイマー画面に到達する。
- バックグラウンドからの復帰と、ログアウト・セッション期限切れ後の再ログインが完了する。
- 許可ユーザーの `/api/health` が正常に表示され、未許可ユーザーは拒否される。

通常タイマー・ポモドーロ・作業選択を実装済みです。上記の操作確認を実機で行ってください。ポモドーロを含む総合検証は issue #6 で行います。

### 確認記録と受け入れ条件

本番配置後に [確認記録テンプレート](docs/access-verification.md) の各項目を埋めます。issue #2 の受け入れには、本番での許可・未許可の画面/API 検証が必要です。利用者から、公開 URL の画面/APIでの認証要求、許可メールへの PIN 送信とログイン、iPad でのログイン成功の報告があります。未許可メールの拒否、他の公開経路、iPadOS の正確なバージョンは別途確認が必要です。

保護漏れがあれば公開入口を無効化してから、対象 Worker、All traffic、関連ホスト、Allow/Bypass ポリシーを見直します。health の503はログイン後に発生するなら、D1 ID・binding・本番マイグレーションの適用を確認します。再デプロイで認証問題を解消しようとして Access を外さないでください。

参考: [Workers の Access 設定](https://developers.cloudflare.com/workers/configuration/cloudflare-access/)、[One-time PIN](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/)、[Access ポリシー](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/)、[Wrangler 設定](https://developers.cloudflare.com/workers/wrangler/configuration/)、[D1 マイグレーション](https://developers.cloudflare.com/d1/reference/migrations/)。

### 作業別タイマー方式と終了音

タイマー動作中は、端末の画面が点灯し、タイマー画面が前面に表示されている前提です。終了音の動作確認・不具合調査もこの条件で行い、画面ロック中・別アプリ使用中・バックグラウンドでの発音は対象外です。

タイマー方式（通常／ポモドーロ）も作業ごとに localStorage に保存し、作業切替・再読込で復元します。未保存・不正な値の場合は通常タイマーを使います。進行中はローカル実行状態の方式を優先します。

開始前は作業・方式・必要なポモドーロ設定を選び「開始」を押します。時間カードや音声確認ボタンは表示しません。ポモドーロの集中・短休憩・長休憩の満了時に終了音を鳴らします。通常タイマーの終了・実績保存、ポモドーロの手動終了や休憩スキップでは鳴りません。開始・再開・次フェーズ開始・休憩スキップの操作から直接音声を有効化し、画面復帰時も既存の音声の再開を試みます。中断・終了したAudioContextは次の操作時に再作成し、suspendedの場合はresumeします。音声の失敗はコンソールに記録し、タイマー進行や実績保存は継続します。閉じた画面やスリープ中の通知は保証されず、端末の音量やブラウザの自動再生制限にも依存します。終了音と方式保存自体に追加のDBマイグレーションはありません。

実機確認（未実施）: iPadOS 15 / Safari 15で通常タイマーの開始・停止・再開と終了・実績保存時に音が鳴らないこと、ポモドーロの複数サイクルの集中・休憩満了音、一時停止からの再開、バックグラウンド・画面ロック・リロード後の復帰と再開を確認してください。音声が使えない場合もフェーズ切替と実績保存が続き、手動音声確認UIが現れないことを確認します。

### 計測中の専用画面（issue #11 / #12）

通常タイマー・ポモドーロの開始後は、ヘッダーやナビゲーションを隠し、時間と操作アイコンだけを表示します。進行中の再読込でも同じ専用画面を復元します。通常タイマーはダークブルー（`#253E49`）で実作業時間をカウントアップ、集中はトマトレッド（`#C94F45`）、休憩はグリーン（`#448A70`）で残り時間を表示します。ポモドーロは1時間未満なら `MM:SS`、それ以上は `HH:MM:SS` です。

下部アイコンで一時停止・再開・終了を操作し、休憩中はスキップできます。終了確認を承認すると通常のアプリ画面へ戻ります。未保存の実績がある場合は再送ボタンから同じ実績を再送できます。ブラウザのFullscreen APIは使用しません。この画面変更に追加のDBマイグレーションはありません。PC・モバイル・iPadでの縦横表示、タッチ操作、フォーカス表示の実機確認は別途必要です。

### 日別タイムライン・実績編集（issue #7）

実績・サマリで日本時間の日付を選び、0:00〜24:00の縦タイムラインをスクロールできます。重なる実績は横に並びます。ブロックまたは実績一覧を押すと、開始・終了日時と休憩合計（HH:MM）を編集でき、実作業時間を再計算します。画面の「休憩」は保存データの `paused_ms`（一時停止合計）です。黄色帯は固定22pxで、停止した時刻や長さを示しません。休憩0秒なら表示しません。

日跨ぎ実績は実績と重なる各日のタイムラインに表示し、各日の0:00〜24:00で区切ります。全実作業時間とセッション数は開始日にのみ計上します。開始・終了日付と全時間を表示し、どの日からも同じ実績を編集・削除できます。短い実績で文字が収まらない場合は、下の実績一覧から詳細を開けます。編集で開始日を変えると、その日へ表示を切り替えます。

実作業1秒未満、終了が開始以前、負の休憩は保存できません。時間が重なる他の実績（前日開始を含む）は警告しますが保存できます。削除時は確認を表示します。編集・削除で再送用の受領記録は変更しないため、元実績の再送で上書き・復活しません。追加のDBマイグレーションはありません。

- `GET /api/sessions?date=YYYY-MM-DD`: 日本時間の指定日と時間帯が重なる全実績を取得（100件制限なし）。日付なしは従来通り最近100件。
- `GET /api/sessions?overlap_start=<epoch ms>&overlap_end=<epoch ms>`: 指定区間と重なる実績を取得（端点が接するだけなら重複扱いしない）。
- `PATCH /api/sessions/:id`: `started_at`、`ended_at`、`paused_ms`をまとめて更新。
- `DELETE /api/sessions/:id`: 実績を削除。存在しないIDは404。

手動確認: 日付前後・今日への移動、ブロックの開始位置と高さ、休憩0秒/ありの帯、重複実績の編集、保存後の再表示、削除のキャンセル/確定、23時から翌日終了する実績の開始日所属を確認してください。

実績画面の時刻・実作業時間・休憩時間はHH:MM形式で表示し、秒は切り捨てます。1分未満は00:00です。編集日時は分単位、休憩入力はHH:MM形式です。変更しなかった項目の秒・ミリ秒は元の値を保持します。
